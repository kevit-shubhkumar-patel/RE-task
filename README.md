# MysteryBox Log Analyzer

A Python 3 log analysis project that uses Python's built-in `re` module to validate log records, extract fields, detect suspicious activity, mask sensitive information, and generate a concise security-oriented report.

---

## 1. Project Overview

MysteryBox is a fictional application that generates logs containing:

- User activity
- API requests
- File downloads
- Failed login attempts
- Payment information
- Potentially suspicious activity
- Malformed log records

The purpose of this task is to practice applying Python regular expressions to real-looking log data.

The program reads `mysterybox.log`, processes each record, performs multiple regex-based operations, and prints a summary report.

---

## 2. Requirements

The program must:

1. Validate log records using a regular expression.
2. Extract timestamps, log levels, and `key=value` fields.
3. Count `INFO`, `WARNING`, and `ERROR` records.
4. Count unique application users.
5. Detect suspicious login records using a positive lookahead.
6. Detect and mask 16-digit card numbers.
7. Detect suspicious downloads.
8. Identify users with at least two failed login attempts.
9. Read the records from a log file instead of hard-coding them.
10. Use Python structures such as `set`, `dict`, and `Counter` for aggregation.
11. Use multiple focused regular expressions instead of one large regex.

# 4. Log Record Format

A valid record follows this structure:

```text
YYYY-MM-DD HH:MM:SS | LOG_LEVEL | key=value | key=value
```

Example:

```text
2026-09-28 09:12:43 | INFO | user=alice | action=login | ip=192.168.1.15
```

Supported log levels are:

```text
INFO
WARNING
ERROR
```

Each record must contain at least one `key=value` field.

# 6. Regular Expressions Used

The project intentionally uses separate regular expressions for separate tasks.

LOG_PATTERN

SUSPICIOUS_FILENAME_PATTERN

# 7. Log Validation Regex

```python
LOG_PATTERN = re.compile(
    r"(?P<timestamp>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2})"
    r"\s*\|\s*"
    r"(?P<level>INFO|WARNING|ERROR)"
    r"\s*\|\s*"
    r"(?P<fields>[A-Za-z_][A-Za-z0-9_]*=[^|]+"
    r"(?:\s*\|\s*[A-Za-z_][A-Za-z0-9_]*=[^|]+)*)"
)
```

### Purpose

This regex validates the general structure of a log record and extracts:

- Timestamp
- Log level
- Complete `key=value` section

Example:

```text
2026-09-28 09:12:43 | INFO | user=alice | action=login | ip=192.168.1.15
```

---

## 7.1 Named Timestamp Group

```regex
(?P<timestamp>\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2})
```

`(?P<timestamp>...)` creates a named capturing group.

The timestamp itself is:

```regex
\d{4}-\d{2}-\d{2} \d{2}:\d{2}:\d{2}
```

Breakdown:

| Regex | Meaning |
|---|---|
| `\d` | Digit |
| `\d{4}` | Four digits |
| `\d{2}` | Two digits |
| `-` | Literal hyphen |
| `:` | Literal colon |
| Space | Literal space |

It matches:

```text
2026-09-28 09:12:43
```

---

## 7.2 Separating Fields

```regex
\s*\|\s*
```

This matches the pipe separator while allowing optional whitespace.

For example, all of these can be handled:

```text
|INFO|
```

```text
| INFO |
```

```text
|    INFO    |
```

### Components

```regex
\s*
```

Zero or more whitespace characters.

```regex
\|
```

A literal pipe character.

The pipe must be escaped because `|` has a special meaning in regex.

---

# 8. Log Level Regex

```regex
(?P<level>INFO|WARNING|ERROR)
```

This creates a named group called `level`.

The `|` operator means OR.

Therefore:

```regex
INFO|WARNING|ERROR
```

means:

```text
INFO OR WARNING OR ERROR
```

This rejects unsupported levels such as:

```text
DEBUG
TRACE
CRITICAL
```

---

# 9. Key=Value Regex

The field section begins with:

```regex
[A-Za-z_][A-Za-z0-9_]*=[^|]+
```

This validates a field such as:

```text
user=alice
```

or:

```text
action=login
```

or:

```text
ip=192.168.1.15
```

---

## `[A-Za-z_]`

The first character of the key must be:

- Uppercase letter
- Lowercase letter
- Underscore

Example:

```text
user
action
ip
user_name
```

---

## `[A-Za-z0-9_]*`

After the first character, the key can contain:

- Letters
- Numbers
- Underscores

The `*` means zero or more occurrences.

---

## `=`

A literal equals sign separates the key and value.

Example:

```text
user=alice
    ^
```

---

## `[^|]+`

This means:

> One or more characters that are NOT `|`.

The `^` inside the character class negates the class.

Therefore:

```regex
[^|]
```

means:

```text
anything except |
```

This allows values such as:

```text
alice
login
192.168.1.15
report_2026.pdf
$125.50
```

while stopping at the next pipe separator.

---

# 10. Non-Capturing Group for Additional Fields

The regex contains:

```regex
(?:\s*\|\s*[A-Za-z_][A-Za-z0-9_]*=[^|]+)*
```

`(?:...)` is a non-capturing group.

It groups the repeated field structure without creating another capturing group.

The final `*` allows zero or more additional fields.

Therefore all of these are valid:

```text
user=alice
```

```text
user=alice | action=login
```

```text
user=alice | action=login | ip=192.168.1.15
```

---

# 11. `fullmatch()` for Validation

The program uses:

```python
match = LOG_PATTERN.fullmatch(line)
```

instead of only:

```python
LOG_PATTERN.match(line)
```

`fullmatch()` requires the **entire line** to match the regex.

This is important for validation because we don't want a line to be considered valid if only its beginning looks correct.

---

# 12. Extracting Key-Value Fields

After validation, the complete field section is passed to:

```python
extract_fields(match.group("fields"))
```

The function splits the fields using:

```python
field_text.split("|")
```

For:

```text
user=alice | action=login | ip=192.168.1.15
```

we get:

```python
[
    "user=alice",
    "action=login",
    "ip=192.168.1.15"
]
```

Each field is then split using:

```python
item.strip().split("=", 1)
```

The result becomes:

```python
{
    "user": "alice",
    "action": "login",
    "ip": "192.168.1.15"
}
```

Regex is used for **recognition**, while normal Python is used for **data processing**.

# 13. Suspicious Login Regex

The suspicious login regex is:

```python
SUSPICIOUS_LOGIN_PATTERN = re.compile(
    r"^(?=.*\|\s*(?:WARNING|ERROR)\s*\|)"
    r"(?=.*\|\s*user=(?P<user>[^|\s]+)\s*(?:\||$))"
    r"(?=.*\|\s*action=login_failed\s*(?:\||$)).*$"
)
```

### Purpose

A suspicious login must contain:

```text
WARNING or ERROR
+
user field
+
action=login_failed
```

The important requirement here is the use of **positive lookahead**.

---

# 14. Positive Lookahead

The syntax is:

```regex
(?=...)
```

It means:

> Check whether the following pattern exists without consuming it.

The regex uses three positive lookaheads.

---

## Lookahead 1 — Log Level

```regex
(?=.*\|\s*(?:WARNING|ERROR)\s*\|)
```

This checks that the line contains:

```text
WARNING
```

or:

```text
ERROR
```

---

## Lookahead 2 — User

```regex
(?=.*\|\s*user=(?P<user>[^|\s]+)\s*(?:\||$))
```

This checks for a `user=` field.

The username is captured using:

```regex
(?P<user>[^|\s]+)
```

`[^|\s]+` means:

> One or more characters that are neither `|` nor whitespace.

---

## Lookahead 3 — Failed Login

```regex
(?=.*\|\s*action=login_failed\s*(?:\||$))
```

This checks that the record contains:

```text
action=login_failed
```

---

# 15. Why Use Lookaheads?

Without lookaheads, we could search for these conditions separately.

But the task specifically requires at least one solution using positive lookahead.

The lookahead approach allows the regex to say:

```text
Does this line contain WARNING/ERROR?
        AND
Does it contain a user?
        AND
Does it contain login_failed?
```

without depending on the exact order of those fields.

---

# 16. Card Number Regex

```python
CARD_PATTERN = re.compile(r"(?<!\d)\d{16}(?!\d)")
```

### Purpose

Find 16-digit card numbers.

Example:

```text
4111111111111111
```

---

## `\d{16}`

Matches exactly 16 digits.

---

## `(?<!\d)`

This is a **negative lookbehind**.

It means:

> The character immediately before the 16 digits must NOT be a digit.

This prevents matching 16 digits that are part of a longer number.

---

## `(?!\d)`

This is a **negative lookahead**.

It means:

> The character immediately after the 16 digits must NOT be a digit.

Therefore:

```regex
(?<!\d)\d{16}(?!\d)
```

ensures that the matched sequence is a standalone 16-digit number.

---

# 17. Masking Card Numbers

The program uses:

```python
CARD_PATTERN.subn(
    "****MASKED****",
    value
)
```

`subn()` performs the replacement and also returns the number of replacements.

For example:

```text
card=4111111111111111
```

becomes:

```text
card=****MASKED****
```

The original card number is therefore not written to the generated JSON file.

---

# 18. Suspicious Download Regex

```python
SUSPICIOUS_FILENAME_PATTERN = re.compile(
    r"(?i)^(?=.*(?:secret|backup|admin|password)).+"
    r"\.(?:zip|exe|sh)$"
)
```

A download is considered suspicious when:

1. The filename contains one of:
   - `secret`
   - `backup`
   - `admin`
   - `password`

2. The filename ends with:
   - `.zip`
   - `.exe`
   - `.sh`

3. Matching is case-insensitive.

---

# 19. `(?i)` — Case Insensitive

```regex
(?i)
```

enables case-insensitive matching.

Therefore these are treated the same:

```text
password
PASSWORD
Password
PaSsWoRd
```

This allows the program to detect:

```text
PASSWORD_backup.EXE
```

even though the suspicious keyword and extension are uppercase.

---

# 20. Suspicious Keyword Lookahead

```regex
(?=.*(?:secret|backup|admin|password))
```

This checks whether the filename contains at least one suspicious keyword.

The non-capturing group:

```regex
(?:secret|backup|admin|password)
```

means:

```text
secret OR backup OR admin OR password
```

---

# 21. File Extension Regex

```regex
\.(?:zip|exe|sh)$
```

The escaped dot:

```regex
\.
```

means a literal `.`.

Then:

```regex
(?:zip|exe|sh)
```

means one of:

```text
zip
exe
sh
```

And:

```regex
$
```

requires the extension to be at the end of the filename.

Therefore:

```text
secret_backup.zip
```

matches.

```text
admin_tools.exe
```

matches.

```text
secret_script.sh
```

matches.

But:

```text
backup_notes.pdf
```

does not match because `.pdf` isn't allowed.

# 22. Python Structures vs Regex

An important design principle in this project is that **not everything should be done with regex**.

### Regex is used for:

```text
Validation
Extraction
Pattern detection
Card number identification
Filename detection
```

### Python structures are used for:

```text
Counting
Aggregation
Unique users
Failed-login totals
Generating the report
```

For example:

### Unique users

```python
users = set()
```

A `set` automatically removes duplicates.

---

### Log level counting

```python
level_counts = Counter()
```

Used for:

```text
INFO
WARNING
ERROR
```

---

### Failed login counting

```python
failed_login_users = Counter()
```

For example:

```text
alice → 5
admin → 2
leo → 1
```

Then Python filters users with:

```python
count >= 2
```

This is much cleaner than trying to make regex perform aggregation.

# 26. Key Regex Concepts Practiced

This project covers several important Python regex concepts:

- Character classes: `[...]`
- Negated character classes: `[^...]`
- Quantifiers: `*`, `+`, `{n}`
- Alternation: `|`
- Capturing groups: `(...)`
- Named groups: `(?P<name>...)`
- Non-capturing groups: `(?:...)`
- Positive lookahead: `(?=...)`
- Negative lookahead: `(?!...)`
- Negative lookbehind: `(?<!...)`
- Start anchor: `^`
- End anchor: `$`
- Escaping special characters: `\|`, `\.`
- Regex flags: `(?i)`
- `re.compile()`
- `fullmatch()`
- `subn()`

# 27. Important Design Principle

The project follows the principle:

> **Use regex to recognize patterns, and use Python to process the recognized data.**

For example:

```python
# Regex identifies the record.
match = LOG_PATTERN.fullmatch(line)

# Python extracts the fields.
fields = extract_fields(match.group("fields"))

# Python performs aggregation.
failed_login_users[fields["user"]] += 1
```

This avoids creating one extremely complicated regex and makes the program easier to understand, test, and maintain.
